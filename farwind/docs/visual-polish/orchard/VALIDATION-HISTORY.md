# 验证过程与首因

第一轮两项新浏览器检查失败，原始结果及截图、trace保存在 `first-check/`。

移动用例选择 `(330,1590)` 作为花床南侧检查点。既有南围栏位于y=1620，脚底扩张后的上界为1595；导航助手额外检查±6像素安全余量，因此该检查点的1596采样落在原围栏占地，寻路无法到达。实际修复没有新增花床或长椅碰撞。将检查点改到同一南侧、留足原围栏余量的y=1580；继续要求实际键盘行走、逐段碰撞和黑猫跟随检查。

地面像素核对初稿假设生成图片主体alpha≥254。实际源图和运行图主体主要为252–253，保留了生成器的半透明边缘与主体，≥254筛选仅94个游戏尺寸像素，达不到初稿100个样本。核对现改为主体alpha≥250，至少1000个样本，按实际alpha计算合成到任意背景的最大通道偏差（255-alpha，加2级采样舍入容差），仍要求95%以上像素匹配；没有删去真正的地面加载核对。图片文件与场景渲染均未为通过检查而修改。

第二轮移动用例完整通过，但地面核对仅28.46%匹配。查到 Phaser `node_modules/phaser/src/textures/CanvasTexture.js:86` 用 `willReadFrequently:true` 创建地表上下文，测试新画布默认走另一种加速路径；浏览器的缩小采样因此不同，即使二者 `imageSmoothingEnabled` 均为true。独立诊断在一致采样时11432个像素全部匹配。最终测试让预期画布使用地表 `getContextAttributes()` 和相同平滑设置，11412个有效样本全部匹配，正式加载和场景重启检查通过。差异来自测试画布配置，未调整生产图片、地表参数或通过门槛来掩盖差异。第二轮原始失败证据在 `second-check/`，最终采样记录在 `behavior/pixel-diagnostic.json`。
